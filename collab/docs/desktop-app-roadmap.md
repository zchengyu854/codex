# 桌面 App 总体开发流程

日期：2026-10-21。目标平台：macOS 首发。

本文是后续开发的主路线，取代旧计划中“以单终端多窗格为最终交付”的定位。阶段 1–8 的实现和证据继续保留；旧阶段 9–11 的任务历史、安装、协议与上下文工作纳入下列桌面阶段，不再以补齐 TUI 为前置条件。

## 1. 最终产品

交付一个可安装、双击启动的独立桌面应用。以 Codex 桌面版的项目导航、对话、代码审查和工具面板体验作为交互参考，突出本项目的一主控、多模型工作 Agent 协作能力。具体界面在 D1 提供可操作原型后确定，不把“类似 Codex”解释为已承诺其全部功能。

用户的完整操作流程：

1. 安装并打开 App，选择本地 Git 项目。
2. 在设置中配置服务商、模型和密钥，查看连接状态。
3. 新建会话，在聊天输入框描述需求和验收条件。
4. 主控拆分任务，工作 Agent 在独立工作区改代码；界面持续显示消息、工具执行、审批和依赖进度。
5. 用户查看文件差异、测试输出和候选提交，批准集成；失败或冲突时能查看原因并发起返工。
6. 退出再打开后继续查看项目、会话和历史结果；中断操作显示真实状态。
7. 用户通过明确的 Git 操作将协作结果带回自己的工作分支，需要推送时明确选择目标。

## 3. 技术路线与边界

建议采用 Tauri 2 + React + TypeScript：既有 Rust core 保留为独立宿主，桌面壳通过受限桥接复用本地 JSON 行协议，前端消费类型明确的命令响应与事件。Tauri 提供桌面窗口及进程间通信机制，详见[官方进程模型](https://tauri.app/concept/process-model/)。这是针对现有 Rust 项目的选型建议，D1 以打包和真实连接探针确认可行性。

```text
桌面界面：项目 / 会话 / 聊天 / Agent / 文件差异 / 终端 / 设置
                         ↓ 受限命令与事件
桌面壳：窗口、系统对话框、宿主进程、启动诊断
                         ↓ 既有本地协议
Rust core：调度、审批、上下文、Git、SQLite、Keychain
                         ↓
Codex 执行进程 → 配置的模型服务商
```

- 桌面壳管理一个宿主；明确同一状态目录的独占规则，重复启动给出可理解的反馈，避免空白窗格。
- 密钥由原生桥提交给 core，保存后清空输入；不写前端持久化、日志、命令行或公开事件。显示保存/缺失/失败状态，不回显密钥。
- 前端不直接操作数据库、Git 或执行任意系统命令；文件访问和终端操作由宿主校验项目/工作区范围及审批策略。
- 事件按会话和任务定位，断开后补读，切换会话时丢弃过期响应；不把上一个任务的数据贴到新任务上。
- 内测可检测并使用已安装的 Codex 执行器；正式安装前确定可分发的执行器方案及版本锁定，不能依赖开发机 PATH 才能启动。
- TUI 保留为开发诊断入口，新增产品交互优先落在 App。

## 4. 分阶段交付

| 阶段 | 交付内容 | 通过标准 |
| --- | --- | --- |
| D0 核心缺口收尾 | 本地复现主控提前结束；检查完成判定、续跑预算与未完成反馈；修复后保留回归证据 | 不把一次模型回合结束等同于完整目标完成；预算耗尽明确报告剩余工作，无无限续跑 |
| D1 桌面骨架 | Tauri 工程、主窗口、基础布局、项目选择、宿主启动/关闭、事件桥、打包探针 | 双击开发版 App，选择测试仓库并显示真实会话；宿主不可用或状态锁冲突时有明确提示 |
| D2 单 Agent 工作闭环 | 模型设置、Keychain 保存、会话列表、聊天流、工具记录、审批、停止、任务结果 | 无需外部终端，完成配置→发送需求→审批→查看改动和检查输出→审查集成；重开可读历史 |
| D3 多 Agent 协作 | 主控与最多三个 worker 的配置和状态；任务列表、依赖、共享记录、历史任务选择与返工 | 一次需求可拆分协作；历史详情绑定明确 taskId；依赖满足前不执行；完成状态与真实产物一致 |
| D4 代码工作台 | 文件树、代码只读预览、差异审查、内置终端、测试输出、冲突处理及结果带回工作分支 | 用户在 App 内检查文件、运行项目命令、审查候选并处理失败；分支与输出位置明确，不丢未提交修改 |
| D5 日常使用与恢复 | 空状态、错误状态、长输出、快捷键、窗口恢复、中文输入、主题、退出与崩溃恢复 | 小屏与长会话可用；关闭窗口行为明确；重启后不误报成功，不自动重放有副作用操作 |
| D6 安装与内测 | .app/.dmg、依赖检测、数据目录、日志脱敏、版本信息、卸载说明、签名/公证及升级方案 | 在独立用户环境按文档安装；无需源码和 Rust；升级保留数据，失败有恢复路径 |
| D7 完整发布验收 | 桌面端本地场景与有界真实模型验收；兼容矩阵、已知限制、发布说明 | 从安装到需求、委派、测试、审查、冲突返工、结果交付和重启恢复均有可核对证据 |

### D0：先定位，不凭模型措辞判完成

已有真实证据：`evidence/stage-8-real-retry.json`。主控成功集成 slug/total 后，以创建报告任务的预告结束，后续任务实际上不存在。先检查现有 `turn/completed`、主控续跑及任务状态路径，再决定最小改动。不要仅靠匹配“现在开始”等自然语言判断任务是否完成，也不要用无限自动续跑掩盖问题。

本地修复和 D1 界面骨架可分别推进。完整真实重放在修复后按新授权执行，不因暂时缺少真实调用授权而停止桌面开发。

### D1–D2：尽早交付能用的 App

主窗口布局：

- 左侧：项目、新建会话、历史会话、设置。
- 中间：对话时间线、任务和工具执行卡片、输入框及停止按钮。
- 右侧可收起：Agent 状态、任务详情、文件预览、差异审查。
- 底部可展开：终端、命令输出和测试结果；完整交互式终端在 D4 接入。

先用本地模拟事件检查布局与状态，再接真实 core；模拟界面显式标记。设置页必须让用户清楚知道保存是否成功、哪个 Agent 未配置、连接测试会调用模型。主流程不要求记住 Ctrl+K 等终端快捷键。

D2 是第一版可试用桌面 App：一个 Agent 可以完成实际代码任务。无需等待高级多 Agent 面板、完整终端或全部协议真实验收完成后才提供可安装版本。

### D3–D4：把已有协作能力变成可操作产品

旧阶段 9 的任务历史与返工直接进入图形界面：按 taskId 查看历史结果、差异、审批和集成；新任务到达不改变当前选择；返工新建任务并保留原任务引用。

代码审查显示基线、候选、验证命令、退出码和集成目标。冲突与测试失败保留工作区；显式放弃前说明影响，继续使用 core 的当前候选归属保护。

内置终端使用真实 PTY，工作目录可见，输入粘贴、窗口缩放和取消可用。用户终端与 Agent 命令执行保持各自的生命周期与审计归属。首版文件预览只读；直接编辑源码和复杂合并编辑器在明确需要后展开。

“集成到协作分支”和“交付到用户工作分支”必须分别展示。D4 明确支持的交付方式及脏工作区、已有分支、冲突和推送失败的处理，不能把模型宣称完成当作代码已经回到用户分支。

### D5–D7：从开发机可用到可安装

执行器版本、Git 检测、Keychain 访问、安装路径中的空格、Apple Silicon/Intel 构建范围都进入发布清单，未验证的架构不标支持。签名与公证依赖有效发布身份；内测包和正式分发包分别标记。

先实现手动下载升级与数据兼容检查。自动更新在签名、更新来源和回滚策略确定后接入，不阻塞第一版内部安装包。

旧阶段 11 的真实 Responses、混合协议及长上下文续作纳入兼容矩阵。未真实验证的路径标记实验性；若要宣称正式支持，必须补足对应验收。上下文压缩需保留权威约束、依赖、任务和审计历史。

## 5. 每个阶段的开发流程

1. 明确本阶段用户操作、受影响接口和验收用例，再开始实现。
2. 先做最小可操作界面；复用 core，缺接口时只补该流程必需的方法。
3. 完成正常流程、加载/空状态、错误反馈、停止和恢复，不只交付静态截图。
4. 用本地 fixture 验证数据隔离、任务归属、审批及文件操作；UI 用实际桌面运行检查。仅按改动范围运行必要检查。
5. 保存版本、场景、预期、观察结果与限制；真实和模拟结果分别记录。
6. 更新文档并交付可运行产物，再进入下一阶段。付费调用和发布沿用明确授权范围。

## 6. 发布范围

首个完整版本包括：macOS App、项目与会话、图形模型配置与密钥管理、聊天和任务流、一主三 worker、历史与返工、差异与测试审查、内置终端、Git 结果交付、本地持久化和恢复、可安装包。

后续按实际工作流安排：Windows/Linux、图片输入、MCP/插件入口、计划任务、远程执行、云同步、完整代码编辑器。它们不列入首版完成门槛；若用户明确优先需要其中一项，调整阶段范围后开发。

当前立即执行顺序：D0 本地定位 → D1 可启动桌面骨架 → D2 单 Agent 闭环 → D3 多 Agent → D4 代码工作台 → D5 恢复与体验 → D6 安装内测 → D7 完整验收。第一份可试用 App 在 D2 交付。
